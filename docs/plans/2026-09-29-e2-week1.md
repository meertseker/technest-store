# E2 week-1 plan


## Research findings (checked against docs and source on 2026-09-29)

**Stripe provider** (`@medusajs/medusa/payment-stripe`, id `stripe` → `pp_stripe_stripe`)
- Options: `apiKey`, `webhookSecret`, `capture` (default false), `automatic_payment_methods`, `payment_description`, `paymentMethodConfiguration`.
- Webhook URL: `{server}/hooks/payment/stripe_stripe`. Local: `stripe listen --forward-to localhost:9002/hooks/payment/stripe_stripe`.
- Events to subscribe: `payment_intent.amount_capturable_updated` (this is the one that authorises when capture=false), `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.partially_funded`. Also `payment_intent.canceled` and `payment_intent.requires_action`, which the provider also handles.
- The provider ignores intents that have no `metadata.session_id`, so a shared Stripe account is safe.
- **Security finding:** `normalizePaymentIntentParameters(extra)` in `stripe-base.ts` passes the client-supplied `data` from `POST /store/payment-collections/:id/payment-sessions` straight into the PaymentIntent. That includes `capture_method`, `payment_method_types`, `payment_method_configuration`, `confirm`, `off_session`, `payment_method` and `setup_future_usage`. A shopper could send `capture_method: "automatic"`, or add Klarna under £30. **Plan:** a store middleware on that route that throws away any client `data` and adds our own server-side values.
- **Hiding Klarna:** we can't allow `payment_method_types` from the client (see above). Leading option for the ADR: the server-side middleware sets `payment_method_configuration` to one of two Stripe Payment Method Configurations ("with Klarna" / "without Klarna"), comparing the cart total against `klarna_min_basket`. It has to be re-evaluated when the cart total changes, because Medusa refreshes the session. Fallback: the Payment Element's `paymentMethodOrder` plus hiding Klarna in the client. That fallback is cosmetic only, so it isn't acceptable on its own.

**Money units:** Medusa v2 stores amounts in major units (49.99 is stored as 49.99, per the skill rule `data-price-format`), and the Stripe provider converts them to pence itself. Brief §4 says "integer pence". Proposal: treat pence as the rule for *our own* code and contracts (settings, trade tiers, email payloads), and convert only at the Medusa boundary. This needs a team decision (E1).

**Click & Collect:** Medusa v2 has native pickup. A stock location can have a "pickup" fulfillment set, and the admin shows "Mark as picked up" for pickup shipping options. E1 owns the location and shipping setup. E2's `markCollected` should wrap the core mark-as-delivered flow and add the capture.

**Notification provider:** extend `AbstractNotificationProviderService` from `@medusajs/framework/utils`, with `static identifier = "smtp"`, `validateOptions`, and `send(ProviderSendNotificationDTO) → { id }`. Export it with `ModuleProvider(Modules.NOTIFICATION, { services: [...] })`. Register it under `@medusajs/medusa/notification` providers with `options.channels: ["email"]`. The Notification module stores every send.

**docker-mailserver:** OpenDKIM is the default. `setup config dkim keysize 2048 domain technest.co.uk` with the default selector `mail`. The TXT record goes at `mail._domainkey.technest.co.uk`. SPF uses `v=spf1 mx ~all` → tighten to an `ip4:` + `-all` record. DMARC starts at `p=none`.

**Caveat for the Klarna ADR:** when the cart changes, Medusa's `refreshPaymentCollectionForCartWorkflow` re-creates payment sessions without going through the store route. A route middleware alone would therefore lose the Klarna choice. Options to check in 2.21.2:
- a workflow hook on the session-creation workflow;
- re-initiating the session from the storefront after cart changes (the starter already re-initiates on the payment step);
- choosing the configuration inside a thin subclass of the Stripe provider, based on the session amount (which is always server-side). This is the likely winner: the amount comes from the server, and no client input is involved.

**Verified in the installed `@medusajs/payment-stripe@2.21.2` (`dist/core/stripe-base.js`):**
- `initiatePayment({ amount, currency_code, data, context })`: `data` is the client data merged with `session_id`. All of it goes through `normalizePaymentIntentParameters`, and `data.metadata` also ends up in the PaymentIntent's metadata.
- `updatePayment` only updates the `amount` (and returns early when it hasn't changed), so the Klarna choice is never re-evaluated when the basket changes.
- **Decision (goes in the ADR):** a subclass `TechNestStripeService extends StripeProviderService`, with `identifier = "stripe"` and id `stripe`, so it is still `pp_stripe_stripe` and the webhook path doesn't change.
  - `initiatePayment`: calls super with `data = { session_id }` only, plus a server-chosen `payment_method_configuration`.
  - `updatePayment`: calls super, then updates the intent's `payment_method_configuration` when the amount crosses `klarna_min_basket_pence`. Check in the Stripe API that a PaymentIntent update accepts this parameter; if it doesn't, cancel the intent and create a new one.
  - Then no route middleware is needed.
  - **Simpler than two PMCs (checked against the Stripe API reference, 2026-09-29):** PaymentIntent create *and* update both accept `excluded_payment_method_types`. So the subclass sets `excluded_payment_method_types: ["klarna"]` when the amount is below `klarna_min_basket_pence`, and clears it otherwise, both on initiate and on every amount update. There's no Stripe dashboard setup and no extra env vars. The Stripe SDK version bundled with 2.21.2 may not have a type for it yet, so a narrow cast is fine.
- `ProviderSendNotificationDTO` = `{ to, from?, attachments?, channel, template, data?, provider_data?, content? }`, and the result is `{ id? }`. This matches the smtp draft.
